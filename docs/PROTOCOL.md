# 花再 Halo PixelBar 协议参考（已实机确认）

本机型号 **VID 0x2D99 / PID 0xA106**（SoC: Jieli，产品名 "花再 Halo PixelBar"）。

本文只写**经过实机验证或官方抓包证实**的内容；推测与未知项显式标注。
证据等级：`[抓包]` 官方 TempoHub 抓包逐字节；`[实机]` 本机实测；`[社区]` 第三方开源实现交叉验证。

---

## 1. 连接与设备标识

| 项 | 值 |
|---|---|
| VID / PID | `0x2D99` / `0xA106` |
| 控制接口 | interface 4，`usage_page=0xFF14`，`usage=1` |
| 另一接口 | interface 4，`usage_page=0xFF13`（消费控制，我们不使用） |
| 消费控制 | interface 3，`usage_page=0x0C`（媒体键） |
| 报文长度 | 64 字节定长 |

**必须用 USB-C 数据线连接。** 蓝牙（A2DP/Hands-Free）只承载音频，不承载 HID；
仅蓝牙连接时控制接口根本不枚举。`[实机]`

## 2. 帧格式

主机 → 设备（OUT，report ID `0x2E`）：

```
2E AA EC <cmd> <len_be16> <payload...> <checksum> <00 padding>
```

设备 → 主机（IN，report ID `0x2F`）：

```
2F BB EC <cmd> <len_be16> <payload...> <checksum> <00 padding>
```

* `checksum = sum(帧[1:payload_end]) & 0xFF`（**不含** report ID 字节）`[抓包][实机]`
* payload 上限 57 字节（64 − 6 头 − 1 校验）
* 第三个字节（帧类型）：社区文档有写 `0xED` 的、有写 `0xEC` 的。
  **2026-11-08 受控实验：`EC` 与 `ED` 设备都正常响应，回包字节完全一致**
  （同一 `0x66` 查询两种 tag 都回 `2F BB EC 66 00 02 10 04`）。
  故该字节在本机不被严格校验，两个值可互换。`[实机]`

## 4. 0x17 位图上传 —— 线上格式（本项目的核心资产）

### 4.1 格式

```
1064 字节 = 8 条 133 字节记录
每条 = 5 字节头 `T 00 NN XX XX` + 128 字节图像数据
```

| 字段 | 含义 |
|---|---|
| `T` | 场景类别（game `01` / work `02` / study `03` / cat `04`），**等于上传前 EF 帧的第 7 字节** |
| `NN` | 记录序号 `0..7`，**多图上传时全局连续**（两张图为 `00-07` 与 `08-0f`） |
| `XX XX` | 每场景值 / 帧间隔（抓包见过 `0064`=100ms、`0030`=48ms、`ffff`） |

图像位布局（1024 字节）：

```
payload[(row // 8) * 256 + col] |= 1 << (row % 8)
```

即一个字节对应**同一列的 8 个垂直像素**，LSB 在上。256 列 × 32 行 = 8192 点 = 1024 字节。`[抓包][实机]`

### 4.2 与 TempoHub 本地 .bin 的区别（**这是此前错位的根因**）

```
本地 .bin : 1040 = [16 字节全局头][1024 payload]
线上 blob : 1064 = [5B头 + 128B] × 8
```

两者 **payload 位布局完全相同，仅容器不同**。把本地 1040 直接当线上格式发送时，
设备按 133 字节记录解析，第 i 条 128 列块会漂移 **`5i − 15`** 字节：

| 记录 | 漂移 |
|---|---|
| 0 | −15 |
| 1 | −10 |
| 2 | −5 |
| 3 | 0 |
| 4 | +5 |
| 5 | +10 |
| 6 | +15 |
| 7 | +20 |

症状：**粗图案看着正常，细线/小字全毁，且每个分块各自偏移**。`[抓包][实机]`

### 4.3 上传时序

| 步骤 | 主机发送 | 设备回复 |
|---|---|---|
| start | `17 [00 00 <size_be32>]` | `00 01 00 32`（`00 32` = 每块 50 字节） |
| data | `17 [00 02 <seq_be16> <≤50B>]` | `00 03 <seq>`（逐块 ACK；`00 05` = 完成） |
| end | `17 [00 04]` | `00 05` |

* 停止等待式：一次一块，约 50ms/块
* 全原始 1064 字节需 22 块；21280 字节（20 帧）需 426 块
* 上传期间设备屏显示「图片上传中…」，**该提示由固件绘制，无法从主机侧抑制** `[抓包]`

### 4.4 多帧动画

**设备固件自带多帧动画引擎**：上传多图后设备**自行循环播放**，无需主机逐帧推送。
实测 20 帧 / 21280 字节正常播放，该值即槽位容量上限。`[实机]`

> 这一点在社区抓包文档里明确标注为"播放行为未知"，本项目实机确认会播放。

帧间隔由记录头的 `XX XX` 指定（`0x0064` = 100ms 可用）。

### 4.5 槽位与显示

* `0xEF 01 <cat> <opt>` = **选上传目标**（屏进入"上传中"状态）
* `0xEF 02 <cat> <opt>` = **显示该槽位** ← 上传后必须补这一条，否则屏不切换

上传后需等待约 2 秒让固件提交 flash，过早切换会显示「上传失败」。`[社区][实机]`

### 4.6 表情槽位架构（瞬时切换的关键）

**每个表情占独立的一个 category**，表情图用 0x17 一次性"烧"进去；
运行时切换只是发一条 `0xEF` 命令（**约 2ms**），**不需要重新上传**。
category 内部换 slot 才需要重传（慢），所以运行时绝不这么做。

| category | 用途 | 本机可用性 |
|---|---|---|
| 0 | 原生时钟（待机） | 原生 |
| 1 | 原生游戏 | 原生 |
| 2-6 | 自定义内容（表情/图片/动画） | ✅ **实测可存放并显示** |
| 7 | cyber | ❌ **不可用**：切到 7 进入设备原生循环动画，自定义图不显示 |
| 8 | 原生频谱 | 未验证 |

**category 7 的坑（2026-11-08 实机定位）**：往 category 2-7 各推一个大号数字，
切类别后 2-6 全部正确显示对应数字，**唯独 7 显示的是设备原生动画**。
即"协议 ACK 成功 ≠ 图写进去了" —— 0xEE 回读只能确认类别/槽位，
**不能确认内容**，所以排查这类问题必须用大号数字/边框等不可认错的测试图。

这个架构把"慢的上传"和"快的切换"彻底分开，是让音箱做表情/状态指示的核心设计。
本工具 `faces` 命令即按此实现（思路借鉴 wafer-pixel，代码自研）。

⚠️ 占用 category 2-6 会覆盖这些类别的原生场景（办公/阅读/猫/狗/热词）；
官方 TempoHub 可重新选择/上传原图恢复。`[社区][实机]`

## 5. 文本（0xE8）

```
payload = 00 <n> <utf8 bytes>
```

限制：**16 字符 / 48 UTF-8 字节**（超出需自行截断）。

> ⚠️ **payload 首字节必须为 0x00。** 它与第二字节组成通用帧长度字段；
> 填非 0 会让设备按 256+ 字节解析一个 64 字节包 —— 实机复现 **USB 立即掉线、
> 不再枚举，须断电重启**。社区 HaloLyricSync 声称此处是"颜色索引 0-6"，是错的。`[实机]`

对齐 / 滚动（`0xEF`）：

| 功能 | payload |
|---|---|
| 静态对齐 | `01 <RGB> 00 02 00 <align> FF`（align: 0左 1中 2右 3两端） |
| 设备侧滚动 | `01 <RGB> 00 02 01 <0\|1> FF`（0=左到右，1=右到左） |

## 6. 场景 / 时钟 / 频谱（0xEF）

| 类型 | payload |
|---|---|
| 场景 | `02 <RGB> 00 01 <cat> <tpl> FF` |
| 图案/时钟/频谱 | `01 <RGB> 00 01 <idx_hi> <idx_lo> FF` |
| 主题色 | `03 <RGB> ...`（9 字节形式 `03 RGB 00 00 FF FF FF`） |

场景类别：`0`时钟 `1`游戏 `2`办公 `3`阅读 `4`猫 `5`狗 `6`热词 `7`赛博 `8`频谱

图案索引：时钟 `0x0000`~`0x000A`（11 种）；频谱 `0x0800`~`0x0803`（柱状/波浪/对称/密集）

**选场景需发两包**（category + option），只发 category 时回读会变但屏不切换。`[实机]`

单色屏**没有逐像素彩色**，`RGB` 是整屏色调。

## 7. 氛围灯（0x6A / 0x6B）

回读 44 字节：`13 <当前效果> + 7 条 6 字节 <id><R><G><B><亮度><速度>`

设置：`0x6B payload = 13 <effect> <RGB> <brightness> <speed>`

| 效果 | id |
|---|---|
| 呼吸 | 1 |
| 潮汐 | 2 |
| 纯色 | 3 |
| 波纹 | 4 |
| 光影 | 5 |
| 动态光影 | 6 |
| 总开关 | 7（编码在 B 通道，亮度/速度填 `FF`） |

亮度 `0x14`/`0x28`/`0x3C`（低/中/高），速度 1–10。
**设置需连发 3 次（间隔约 30ms）才生效。** `[实机]`

---

## 8. 回读（0xEE）

```
00 <主题色RGB> 00 <模式> <参数...> FF
```

模式：`0x01` 场景、`0x02` 自定义文本、`0x03` 主题色。

**没有屏幕内容读回接口。** 官方 TempoHub 全部 `*_query_parse` 只返回配置，
自定义图片只走 0x17 单向推送。要"读屏"只能靠摄像头或目视。`[实机]`

## 9. 已知边界与未解项

| 项 | 状态 |
|---|---|
| 无屏幕内容读回 | 确认（官方协议无此接口） |
| 原厂 0x17 会写外部 SPI Flash + 图像元数据 | 社区结论；故不适合高频刷新（本工具靠设备自播动画规避） |
| 记录头 `T` 的完整语义 | `T` = 类别已确认；是否用于寻址槽位未验证 |
| `XX XX` 的完整语义 | 疑似帧间隔；多帧播放节奏受其影响 |
| 各场景的槽位号 | A106 实测 `option=0` 可用；社区在 A160 上抓到 `{2:10, 3:9, 4:3, 5:0, 6:0, 7:15}` |
| `0xEF` 第 5 字节（group） | 语义未知，实测取回读值即可 |
| 面板 10px 横向偏移 | 社区在 **A160** 上校准（整图右移 10 列 + 每 unit 第二条 8 行带再左移 10 列）；**A106 实测无需补偿** |
| 固件升级（DFU） | 未验证 |

## 10. 验证方法（可复现）

```bash
python pixelbar.py selftest          # 27 项离线自检，含 3 组官方抓包逐字节复现
python pixelbar.py replay --capture 23   # 原样回放官方抓包 OUT 帧，验证链路
python pixelbar.py border            # 推 1px 满边框，肉眼确认像素级对齐
```

`selftest` 会用 `community/ethan71950701__PixelBar-Display-Hook/tests/fixtures/captured_uploads.json`
里的官方原始字节，把 payload 解码后用本工具的编码器重编，要求**逐字节一致**。
这是防回归最硬的测试。
