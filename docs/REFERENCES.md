# 参考来源与有效性评估

记录本项目参考了谁、哪些内容**实际有效**、哪些是**错误或误导**，便于后续排新问题时
快速判断该信谁、该避哪些坑。

评估分级：
**✅ 关键** = 直接决定成败；**🟡 有用** = 提供了正确线索或旁证；
**⚠️ 有误** = 结论错误，照做会踩坑；**➖ 无关** = 方向不符，仅作负面证据。

## 1. 社区开源项目

### ✅ ethan71950701/PixelBar-Display-Hook —— 本项目的决定性来源

<https://github.com/ethan71950701/PixelBar-Display-Hook>

**贡献**：25 次官方 TempoHub 操作的 USB 抓包分析（163KB 协议文档），并附带**原始抓包
fixtures**（`tests/fixtures/captured_uploads.json`）。

**有效内容**：

* 0x17 线上格式 = `1064 字节 = 8 条 133 字节记录`，每条 `5 字节头 T 00 NN XX XX` + 128 字节图像
* 上传时序 start/data/end 与设备的 ready/ACK 回包格式
* `T` = 场景类别，且等于上传前 EF 帧第 7 字节
* 图像位布局 `(y//8)*256+x`，LSB 在上（用笔画连续性 + 渲染可读性双重验证）
* 多图上传时记录序号 `NN` **全局连续**
* 原厂 0x17 会显示「图片上传中」，无法抑制

**它自己标注的未知**（后来被我们补上）：

* `XX XX` 语义（我们推断为帧间隔）
* **多帧是否会被设备播放**（文档写"播放行为未知"）→ 本项目实机确认**会播放**

> 这份 fixtures 是本项目最硬的资产：`selftest` 用它做逐字节回归测试。

### 🟡 Serius117/wafer_pixelbar_public —— 有用，但格式解析有误

<https://github.com/Serius117/wafer_pixelbar_public>

**有效内容**：

* 完整的可用上传器实现（选类别 → 选槽位 → 上传 → 等提交 → 切显示）
* **上传后需等约 2 秒**再切换，否则显示「上传失败」
* `0xEF 01` 只选上传目标、`0xEF 02` 才显示槽位
* 各场景槽位号（A160）：`{2:10, 3:9, 4:3, 5:0, 6:0, 7:15}`
* 面板校准思路（安全区、逐帧共用变换避免动画抖动）

**⚠️ 有误内容**：

* 把格式解析成 `2 × (20 字节 unit 头 + 512 字节)` —— **错误**。
  实测官方抓包里第 5 条记录的头是 `T 00 04 XX XX`，`NN=4` 只是**记录序号**，
  被误读成了 `unit_index*4`（1×4=4，巧合）。按此格式发送会让每条 128 列块
  漂移 `5i−15` 字节。
* 其"整图右移 10 列 / 每 unit 第二条 8 行带再左移 10 列"的校准是在 **PID 0xA160**
  上做的；**本机 A106 实测无需任何补偿**。

**✅ 关键设计（值得借鉴，本工具 `faces` 命令即按此实现）**：

* **表情槽位架构**：每个表情占**独立的一个 category**，图一次性用 0x17 烧进去；
  运行时切换只发一条 `0xEF` 命令（约 2ms），**不需要重新上传**。
  category 内部换 slot 才需要重传（慢），所以运行时绝不这么做。
* 表情 → category：`2=normal 3=happy 4=sad 5=angry 6=thinking 7=celebrate`；
  0=原生时钟、1=原生游戏、8=频谱 保留不动。
* 把"慢的上传"与"快的切换"彻底分离，这是让音箱做表情/状态指示的核心思路。
* 脸部几何：`SPREAD=36`（双眼在中心两侧 ±36），即**宽脸**设计 ——
  8:1 超宽屏不能把方脸缩在中间（那样只剩一小块）。

### 🟡 SilverlingFox/dsh-pixelbar —— DSH 插件形态，但位图能力为零

<https://github.com/SilverlingFox/dsh-pixelbar>（已发布到 npm）

**有效内容**：

* **颜色校准表**：实测这块屏 **R 通道增益偏低、B 偏强**，直接发 sRGB 会偏青/偏紫；
  给出逐色补偿映射（如 `#F0B4C8 → #FF6080`、`#FFFF00 → #FF8800`），
  并配 `docs/color-card.html` 色卡供目测校准。**这是本项目没有的能力。**
* **推完自动回时钟**（默认 15 秒），适合当通知用 —— 避免通知一直挂在屏上。
* DSH 插件封装：注册单个 `pixelbar` 工具，聊天里直接说"像素屏推个『在』"即可调用。
* Windows 细节：用 `pythonw.exe` + `windowsHide` 规避控制台闪窗；连接带重试。

**⚠️ 需要注意**：

* README 声称"推文字 7 种颜色"，但代码里 `build_text_packet(text, color)` **完全忽略
  color 参数**，`send_text` 也从不传它 —— **是死代码**，实际文字色固定为默认值。
  （好在它没有去填 byte4，否则会触发下面那个掉线坑。）
* **完全没有 0x17 位图/动画能力**，无自定义图片、无 GIF、无表情槽位。
* 帧类型字节用 `0xED`（我们用 `0xEC`）。2026-11-08 受控实验证明**两者设备都接受**，
  回包字节完全一致 —— 这个分歧不影响互操作。

### 🟡 FerrinWang/pixelbar-studio —— 独立旁证

<https://github.com/FerrinWang/pixelbar-studio>

**有效内容**：

* 独立确认线上格式为 **1064 字节**（"设备文件是 1064 字节：将 raw 1024 切为 8 段，
  每段 128 字节"）—— 与 ethan 的结论互证，这是我们敢于否定自己旧结论的重要依据
* 上传完成后需发 `[group=0, mode=1, opt0=3, opt1=4]` 显示
* 确认「图片上传中」提示无法从主机侧抑制

**注意**：目标是 **PID A160**，槽位号与面板偏移与本机 A106 不同。

### 🟡 woozyc/pixelbardiy（HaloStudio）—— 同型号 A106，指出了另一条路

<https://github.com/woozyc/pixelbardiy>

**有效内容**：

* **明确写着 PID 0xA106**（与本机同型号），像素索引 `data[(y//8)*256+x]` 与官方一致
* 揭示原厂 `0x17` 是**资源保存路径**：会写外部 SPI Flash 和图像元数据，
  故每帧上传会出现「图片上传中」并反复擦写存储 → **不适合高频刷新**
* 因此他们给显示 MCU 打了补丁，用 **HPL2** 协议直接写 RAM 帧缓冲：
  op 1/2/5 = 接管/心跳/释放，op 6/7 = 编码帧 BEGIN/DATA，
  codec 0=原始 / 1=RLE / 2=XOR-RLE，CRC-CCITT，单片 ≤37 字节，
  带本地动画引擎（推入/横向揭幕，interval 8–64ms）

**对本项目的意义**：我们不需要走刷固件这条路 —— 设备**自带的**多帧动画引擎
已经够用（见 PROTOCOL.md §4.4）。

### ➖ traceless929/PixelBar、EnderCHX/pixelbar-sdk

第三方 SDK/客户端，README 明确写 **"0x17 帧上传不在支持范围内"**。
作为**负面证据**有效：印证了直接写帧缓冲这条路的难度。

### ➖ Seraph310/halo-pixelbar-mcp

<https://github.com/Seraph310/halo-pixelbar-mcp>

只覆盖文本 / 场景 / 氛围灯 / 音量，**完全没有 0x17 位图推送**。
其 PROTOCOL_NOTES 与我们的帧构造一致（旁证），但对位图问题无帮助。

### ➖ OpenRGB Edifier Halo 驱动

`Controllers/EdifierHaloController/` 已合入 OpenRGB，但
`RGBController_EdifierHaloPixelbarScreen` 只做主题色与内置场景，
**不推自定义位图**。

### ➖ HaloPixelToolBox（git.xfe.studio / GitHub XFEstudio）

WinUI3 歌词工具，只经 `0xE8` 发文本；其 `PixelSceneUploadProgress` 是**未接线的空壳**。

## 2. 社区实现中发现的**错误结论**（务必避开）

| 来源 | 错误说法 | 实际 |
|---|---|---|
| **HaloLyricSync** | 文本帧 byte4 是"颜色索引 0-6" | **危险错误**。byte4 与 byte5 组成通用帧长度字段，填非 0 会让设备按 256+ 字节解析 64 字节包 —— 实机复现 **USB 立即掉线，须断电重启**。原版 C#（HaloPixelToolBox）恒填 0 才是对的 |
| **wafer_pixelbar_public** | 线上格式是 `2×(20B unit 头 + 512B)` | 实为 `8×(5B 头 + 128B)`；`NN=4` 被误读成 `unit_index*4` |
| **官方用户说明书** | "128×64 logical page buffer" | 把分页顺序调研引向歧途；实机四象限探针证实 **page-major（先上排左右、再下排左右）** 才是对的 |
| **本项目早期结论** | "官方 1040 才是对的，社区 1064 是错位根因" | 1040 是 **TempoHub 本地文件格式**，1064 是**线上格式**，两者 payload 位布局相同、仅容器不同；把 1040 当线上格式发才是错位根因 |
| **本项目早期结论** | "unit 头第 3 字节必须为 unit_index*4" | 同 wafer 的误读，实为记录序号 `NN` |

## 5. 方法论上真正起作用的三件事

1. **拿到官方原始字节（ground truth）**
   ethan 的抓包 fixtures 是转折点。此前所有争论都建立在"渲染出来像不像"上，
   有了官方字节就能做**逐字节比对**，一切推测立刻可判真假。

2. **用"渲染可读性"而不是数值指标做判决**
   两种格式解析的"横向笔画连续性"只差 0.009（0.942 vs 0.933），无法区分；
   但把 1024 字节渲染成图后，一种清晰显示「兼职成年人」，另一种是乱码 —— **一眼可判**。
   遇到指标区分度不足时，换成人类可直接判读的证据形式。

3. **区分"本地文件格式"与"线上传输格式"**
   1040 与 1064 争论了很久，根因是把两个不同层的东西当成同一个。
   一旦意识到"本地存 1040、线上发 1064"，所有现象（粗图案正常、细线全毁、
   每块各自偏移）立刻得到统一解释。

## 7. 本项目相对社区的位置

### 我们独有的能力（社区开源实现中均未覆盖）

| 能力 | 说明 |
|---|---|
| **0x17 位图线上格式全链路** | 1064 = 8×133 的编解码，**对 3 组官方抓包逐字节复现**。traceless929 与 EnderCHX 的 SDK 都明确写"0x17 不在支持范围内" |
| **GIF / 图片 → 256×32 转换管线** | 极性处理、并集包围盒防抖、横穿/原地两种运动、地面线、抖动、alpha 通道、纯色底剔除、长循环均匀抽样 |
| **二次元角色动画库 + 精灵表切片** | 精灵表连通域切片、视差背景、"原地走 + 背景滚动"的无缝循环约束、导出 256×32 GIF |
| **多帧动画 + 设备自播** | 20 帧上限实测；**"设备会自己播放动画"这一点社区抓包文档标注为未知，本项目实机确认** |
| **表情槽位架构实现** | 借鉴 wafer 的思路，代码自研；烧录 + 2ms 切换 |
| **离线自检与回归测试** | 42 项检查，含官方抓包逐字节复现 —— 改坏了立刻能发现 |
| **库 + CLI 双层 API** | 既能命令行用，也能 `from pixelbar import wire` 当库用 |
| **音频播放集成** | 把音箱当声卡放歌并联动频谱（音箱的本职，社区项目都没做） |

### 社区有而我们没有的（值得补）

| 能力 | 来源 | 价值 |
|---|---|---|
| **颜色校准表** | dsh-pixelbar | 这块屏 R 偏弱、B 偏强，不校准发色会偏青紫 |
| **推完自动回时钟** | dsh-pixelbar | 当通知用时避免内容一直挂着 |
| **DSH 插件封装** | dsh-pixelbar | 聊天里直接调用，无需记命令 |
| **自写固件做实时流** | woozyc（HPL2） | 真·高刷新的唯一路径，工程量大 |

### 结论

增量**足够大且有明确差异**：社区现有的开源实现（SDK、插件、歌词工具）
**没有任何一个能推自定义位图或动画**，而这是本项目最核心、验证最扎实的部分。
同时本项目补上了社区一直缺失的**可复现验证手段**（官方抓包回归测试）。

若要发布，建议先补三件事：
1. **颜色校准表**（可参考 dsh-pixelbar 的实测值，或自行做色卡校准）
2. **推完自动回时钟**（几行代码）
3. 明确标注**不覆盖**哪些社区能力，避免与已有项目重复造轮子

许可证方面（发布前必须处理）：
1. 5×7 字库来自 MIT 的 claude-edifier-pixelbar-usage，需保留其署名与许可（见 §4）；
2. **角色美术 `gifs/oga/` 来自 David Revoy 的 Pepper&Carrot，授权 CC-BY 4.0 / 3.0，
   必须署名**（作者声明非商业可免，但仍应注明）。`anims --export` 已把署名写进
   GIF 的 comment 段；若把素材或派生图一并分发，请同时保留 `docs/README.md`
   与 `pixelbar/chars.py` 中的署名段落。

## 8. 素材来源评估（"去哪儿找二次元图"）

### ✅ Pepper&Carrot 24×32 角色表 —— 本项目最终采用的素材

| 项 | 内容 |
|---|---|
| 来源 | <https://opengameart.org/content/24x32-peppercarrot-characters> |
| 作者 | **David Revoy**（改编自网络漫画 Pepper&Carrot 的线稿） |
| 授权 | **CC-BY 4.0 / CC-BY 3.0（须署名，不是 CC0）** |
| 结构 | 左上角 **3 列 × 4 行、每格 24×32**；每行一个朝向（背/侧/正/另一侧），每列一个行走帧；右侧是人像大图 |
| 为什么好 | ① 原生 24×32，**与 32 像素高的屏等高，无需缩放**，像素不糊；② 动漫画风；③ 行走循环现成 |

**踩坑**：该表底色是**双色**（青绿角色区 + 灰色人像区）。用"边框采样取底色"
（`auto_background`）会返回 `None`，于是退化成亮度阈值，把整块青绿背景当成前景，
切出来每格 768/768 全白。正确做法是**在要切的网格区域内**取颜色众数当底色。

### ⚠️ GifCities（Internet Archive 的 GeoCities GIF 归档）—— 采了 1877 张，结论是不合适

GifCities 的搜索页可直接解析出 `https://blob.gifcities.org/gifcities/<ID>.gif` 直链，
另有 `special-search?q=&width=&height=&page_size=200&offset=` 支持**按精确宽高检索**
（本项目据此采了 468×60 / 400×50 等 8:1 横幅共 497 张）。

实测结论（采集 1380 张动漫关键词 GIF + 497 张宽幅横幅）：

| 发现 | 说明 |
|---|---|
| **主体是"网页家具"不是画** | 结果大量是 Web Ring 按钮、`About Us` / `Take Me Away` / `Need Help?` 文字横幅、导航条 |
| **文字横幅会骗过数值评分** | 文字笔画干净、缩到 28px 存活率高，一度占据榜首。必须加**连通域个数**指标才能区分"画"（1-3 个块）与"文字"（几十个碎块） |
| **少数角色图也不够看** | 90 年代低分辨率剪贴画缩到 28px 后只剩难以辨认的剪影，远不如原生 24×32 的像素画 |
| 例外 | 少数"一排 chibi 角色手拉手"类横幅确实可爱，但样本太少，不足以撑起功能 |

**方法论**：素材源要按"**是否原生匹配目标分辨率**"来选，而不是按"名字里有没有 anime"。
原生 24×32 的像素画 > 高分辨率动漫图 > 低分辨率网页剪贴画。

采集/评分工具保留在 `tools/`：`gc_harvest.py`、`gc_banner.py`（采集）、
`gif_rank.py`（评分，含存活率/墨量/运动/连通域）、`gif_sheet.py`（拼图肉眼筛）、
`anim_preview.py`（横穿动画预览）。

## 9. 设备固件卡死（连推多个动画时）

**症状**：连续上传多个多帧动画时，设备可能在提交 flash 阶段卡死，之后
**持续刷** `2f bb ec 17 00 04 00 03 <seq>`（seq 每秒涨十几个），HID 写返回 -1，
所有命令超时。软件无法恢复，**必须断电重启**（拔插 USB-C 数据线或关机重开）。

**根因（推断）**：数据阶段的 ACK 未校验块序号。上一次上传残留的 ACK 会被
当成本次某一块的 ACK，导致 `index` 与设备实际期望的块号错位，设备卡在等某一块。

**已做的修复**：

1. `_read_state(..., accept=..., seq=...)`：start 只认 `STATE_READY`(0x01)，
   数据 ACK 必须**序号匹配**，残留 ACK 直接跳过（`wire.py`）；
2. `assert_link_healthy()`：上传前体检，设备若在刷 ACK 就直接报错并提示断电，
   而不是继续发帧把它搞得更乱；
3. `anims --burn` 默认 `--settle 4 --gap 1`，并提供 `--only` 分批烧。

**注意状态常量方向**：`0x00/0x02/0x04` 是**主机发**的值，`0x01/0x03/0x05`
是**设备回**的值。早期代码把设备回的 `0x01` 写成裸数字，很容易在重构时搞错。
